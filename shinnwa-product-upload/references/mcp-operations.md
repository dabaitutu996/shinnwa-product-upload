# MCP 执行与恢复

## 只读准备

连接依赖已配置的 `medusa_catalog`，目标服务为 `https://shinnwaapi.chaoxian.online/catalog-mcp`。同事的电脑必须另行配置其授权凭据；技能元数据不自动提供认证。工具名的前缀随客户端可能变化，按实际工具定义调用，不伪造未暴露的工具或参数。不通过修改客户端配置、用网页自动化或手工 HTTP 绕过工具审批。

先读取实际工具说明，再读 `list_catalog_options` 识别分类等可选项。通过 `list_products` 以 SKU、商品名等相关线索查询并人工核对返回规格的 ID、SKU、各 GTIN 字段、handle、状态和 `product_url`。不要假定 `query` 一定精确匹配 SKU／GTIN。

当前 `list_products` 有 `query` 和 `limit`（1–100），没有声明分页。结果 `count` 大于实际返回长度、结果达到上限或查询匹配规则不明时，缩小查询逐项检查；仍不能排除时标记“可能重复，待核实”，不可说已遍历全店。已有后台 ID／URL 的行先读取对应商品核实，不能仅因表中写“成功”就信任。源表 `Product ID` 在基准格式中是 UPC，绝不能拿它当后台商品 ID 查询或覆盖。

| 当前接口 | 使用原则 |
| --- | --- |
| `list_products` | 查重、确认规格 ID、最终读回和获取链接；只读 |
| `list_catalog_options` | 获取真实可用 ID，不把分类名称直接当 ID |
| `upload_product_image_data` | `file_name` 与 Base64 `data`／data URL；确认后才调用，保存返回图片 URL |
| `create_product_draft` | 传确认后的最终字段；`variants` 含确认的原有／生成 SKU、各自价格、Color／Size 选项和原生 `upc` |
| `create_product_drafts_batch` | 最多 100 件商品一批，逐商品核对返回结果；不能假定事务回滚或全成功 |
| `update_variant_gtin` | 参数 `product_id`、`variant_id`、字符串 `gtin`、明确的 `field`；`null` 清空，仅获明确批准时用 |
| `publish_product` | 只发布已读回核对且清单中获批上架的草稿 |
| `delete_product` | 本上传流程不使用；失败不意味着有权删除或重建 |

现有工具没有通用商品编辑接口。查到既有商品需要改价格、标题、图片等时，说明当前接口不能执行该修改并请求处理办法；不能新建一个同款来假装更新成功。

同一商品组只有部分 SKU 已存在时，先核实它们是否属于同一父商品。若要把新颜色／尺寸加到该既有商品，而当前工具未提供新增规格能力，暂停该组并说明限制；不能过滤已存在 SKU 后把剩余规格另建成同款商品。

## 写入顺序

1. 在源文件夹创建唯一运行目录，例如 `Shinnwa上传记录/20261028-153000-01/`；有同名目录则用新编号，不覆盖历史。写下输入文件和图片指纹、确认版本与范围、已确认的数据、源行映射。只记录本任务所需资料，不保存密钥。
2. 执行前重新检查输入指纹并查重。只对清单批准的新商品上传图片，保存“图片相对路径＋文件指纹 → 返回 URL”；恢复时复用未变更且明确上传成功的图片。没有确认的图片不能因为“先传了再说”而上传。
3. 图片完成后组装草稿参数，逐 SKU 对照确认清单。商品 options 与各 variant 的选项组合必须一致；价格单位须已核实。UPC 保持字符串并提交到每个规格的 `upc`，不是只写入 metadata；`Product ID Type` 明确为 UPC，原表其他必填资料也须已完整确认。保存本次尝试与商品键后再调用创建接口，不给接口添加未声明的幂等参数。
4. 收到结果立即记录商品和规格 ID。重新查询核对实际标题、SKU／选项、价格（查询不返回时使用可用的可靠读回方式，无法读回要明确）、GTIN、图库和状态等关键字段；任何关键不一致停止该商品的发布。若无法完成必要读回核对，保持草稿并报告“待核对”，不能把假设当审核完成。
5. 只有预览已明确批准上架，且草稿核对通过才调用发布。此时无需重复索要同一发布许可；若新发现问题或改变资料则重新确认。发布后查明状态，不以“发出了调用”算成功。
6. 获取服务端 `product_url`，缺少时用已保存 ID／SKU 缩小查询并精确核对身份再取。不得根据其他商品的链接规则拼接。保存最终结果并按表格规则回填。

### Windows 图片传参

当前上传工具要的是文件实际内容的 Base64，不是本地路径。可用 PowerShell 的 `[System.IO.File]::ReadAllBytes($imagePath)` 和 `[System.Convert]::ToBase64String(...)` 获取编码，再通过客户端支持的工具编排／参数传递能力交给图片工具；不要要求同事手工复制长编码，不要把整段编码显示到聊天。原始文件名作为 `file_name`，每张图片分别调用，核对返回值确为对应的图片 URL。

上传前检查原文件大小和客户端参数／输出上限。编码比原文件大约多三分之一；不能只检查服务端 15 MiB 限制而忽略本地工具传递截断。当前客户端无法完整传递内容时，停止并说明需要可用的文件上传能力；不可把截断字符串、文件路径或伪造图片 URL 传给接口，也不可绕开审批直接向后台写入。任何压缩或格式转换仍须经确认。

## GTIN 修改

先查到准确的商品和规格 ID，将旧值、拟写入值、`field`、SKU 放入确认单。调用前再读一次旧值，若已发生变化先暂停，不能覆盖别人的更新。修改后读取该规格，核对目标值及其他标识字段仍正确。返回不确定则先查询实际值，不盲目重试。只确认修改 GTIN 不附带发布许可。

## 中断、重试和部分成功

运行记录按商品保存：稳定商品键、工作表与源行、所有 SKU、确认版本、输入指纹、调用阶段、尝试时间、图片 URL、商品 ID、规格 ID、远程状态、`product_url`、错误和回填状态。至少区分“未开始／图片已上传／创建中／草稿已创建／已核对／已发布／失败／结果待核实”，并独立记录“未回填／已回填／回填失败”。每次远程调用前记意图，有确定结果后立即更新，采用本地临时文件加替换保存，避免半写记录。

- 远程调用超时不表示没有成功。遇到创建／批量响应不完整、断线或进程中断，先按既有记录和 SKU／商品键查找；唯一核对成功才继续，多个候选或无法确认则停在“结果待核实”。不能因查不到一次就重新创建。
- 批量失败逐项对账：已创建的继续其阶段，确定未创建且错误已修复的才可重试；修复改变了批准内容时须再确认。未知项不加入新的创建批次。
- 图片调用结果不明先检查可用服务端结果；无法找回时停止该项并说明，不反复上传产生多份文件。无删除接口也不代表允许任意遗留重复图。
- 发布结果不明先查状态；已发布不重发。创建成功但发布失败仍是“草稿已创建，发布失败”，不能算创建失败后再建。
- 外部状态与表格状态分开记录。原表被占用、磁盘满、所选表格工具故障等不回滚远程商品，不触发再次上传。保留全部结果，在可写后只重做回填。
- 后续用户说“继续上次”时加载原确认单和记录，核对当前资料和目标店铺；只恢复仍获授权、数据未变更的未完成阶段。没有可验证记录或输入变化则重新预览相关项。
- 指纹记录区分原始商品资料区域与本流程新增的结果列，并保存每次成功回填后的文件指纹。本流程自己的回填不算商品资料变更；继续时仍重新比对商品输入及图片，不能直接跳过检查，也不因仅新增结果就要求重新批准上传。
